# LocalDNS 对照与 rtdns 下一阶段内存优化建议

研究日期：2026-10-27，Asia/Taipei。本轮只读研究、保存报告，未修改产品代码、配置或服务，未启动负载、合并、发布或部署。下述方案是建议，不是实施或改变功能契约的授权。

## 2. 报告哪些结论可用，哪些需要降级

值得借鉴的主线是：**对存储做成本计量、限制工作集、减少小对象和临时复制，再用分配器回收已经释放的内存。** 不是“换 jemalloc 就能把 rtdns 变成10MB”。

| 报告说法 | 本轮判断 |
| --- | --- |
| 四缓存按5:5:1:1分配总预算 | 当前生产 metrics/设置也吻合，可信；这是缓存计量预算，不是进程RSS硬上限 |
| 缓存有条数与成本双约束 | 报告伪代码和预算贴线实测相互支持，值得借鉴；本轮未重复反编译或压测 |
| 严格LRU | 伪代码支持分片内LRU；最旧5万条重放miss不能单独证明全局严格LRU，也不能证明它优于TinyLFU |
| 每条285–302B | 是特定报文/域名/缓存的平均计量成本，不能套用到全部报文、日志或RSS。当前main缓存184条计299926B，平均约1630B，已明显不同 |
| 158MB中其余约70MB都是表/运行时/分配器 | 没有分项分配证据；其中还可能有查询日志、学习表和统计。不能用RSS减cache_bytes直接给分配器定责 |
| `10.3 + cache_bytes × 1.9 + 10`可推导24小时RSS | 只是一个场景的拟合，不是长期上界。报告128MiB总预算也未在四张表同时用尽；没有完成24小时证明 |
| 无serde字符串/依赖痕迹，因此没有serde | 静态链接、strip/LTO可能消除痕迹；只能说未检出。依赖数少也不等于运行内存必然少 |
| jemalloc空闲150秒不降，所以不归还OS | 活数据未释放时不能检验回收效果；观察到峰值回落也不能单独证明由哪个purge路径造成 |
| 每socket收发各2MB，所以每socket8MB | 算术应为每socket合计4MiB、四socket约16MiB配置上限；不是预先分配的驻留量，也不属于用户态RSS |
| 短时稳定说明无泄漏 | 只能说明该短场景未观察到持续增长；不能代替长时间、异常上游和高基数测试 |

jemalloc 的 dirty/muzzy decay 是近似的分阶段清理时间，dirty 可经 MADV_FREE 进入 muzzy，不能简化为“一秒精确归还全部页”。见[jemalloc 手册](https://jemalloc.net/jemalloc.3.html)。Linux 对 SO_RCVBUF 加倍是记账语义，见[socket(7)](https://man7.org/linux/man-pages/man7/socket.7.html)。

报告出现 `rules/rule_bin/policy_hash` 名称，**没有充分证明其域名规则采用何种哈希、是否核对原文、是否mmap或共享压缩索引**。因此不能据该报告断言规则索引比当前rtdns更省，也不据此重新引入概率匹配。

## 3. 当前生产只读观察：差距存在，归因尚未完成

2026-10-27 11:48:32+08:00 开始的顺序 `/proc` 与GET读取，无负载、无配置变更；采样不是原子快照，也不是公平配对基准。原始数值及源码指纹保存在[脱敏快照](localdns-memory-comparison-2026-10-27-snapshot.json)。

| 项目 | rtdns | LocalDNS |
| --- | ---: | ---: |
| RSS，KiB | 61664（60.22MiB） | 25068（24.48MiB） |
| 匿名驻留，KiB | 49016 | 17688 |
| 文件映射驻留，KiB | 12648 | 7380 |
| 线程数 | 3 | 17 |
| 缓存live指标合计 | 41852条 | 19966条 |
| 查询日志实际保留数 | 10749条 | 100000条（分页total_items确认） |
| 缓存计量字节 | 当前没有该指标 | 6448369B，约6.15MiB |

rtdns匿名驻留比LocalDNS多约30.59MiB，文件映射部分多约5.14MiB；这些只是驻留类型差额，不是具体对象的归因。线程更多的反而是LocalDNS，不能把差距简单归因于rtdns线程栈。更不能拿虚拟地址空间VmSize或可执行文件大小代替RSS。

LocalDNS已满10万日志，不能说它是因为日志没填满才省。当前日志API抽样100条，非空应答对象只见`data`键，Trace ID和upstream_attempt均为空。它公开的日志投影明显比rtdns的TTL、RR类型、flags、Trace ID、分支/尝试等诊断契约简单；**这不证明其底层绝不保存其他信息，也不证明全部历史日志都如此**。样本分布和底层布局仍需同负载测量。

当前缓存配置差别更大：

- rtdns：7个缓存，每个`size=20000000`；`lazy_cache_ttl=259200000`秒，即3000天。是上限与保留设置，不是启动分配1.4亿条。此值在当前实现中从存入时间计算完整缓存保留边界，不能简单与另一程序的“fresh TTL + stale窗口”相加模型互换。
- LocalDNS：总预算128MiB，main/domestic各500000条，foreign/foreign_ecs各100000条，`stale_ttl=604800`秒（7天）。当前仅计量约6.15MiB，尚未触发总预算。
- rtdns缓存live数约为LocalDNS两倍，但缓存层可重复保存同一名字，不是两倍独立域名；上游/分流/更新时间和运行历史也不同。不能由这些快照算每条RSS或“同功能节省百分比”。

**3000天保留意味着很少有正向缓存会自然走到完整过期边界。** 所以“主动清过期缓存”虽值得完善，却未必立刻省很多；想明显限制长期工作集，还需讨论容量、字节预算或保留周期的取舍。

## 4. 当前rtdns对应实现

| 维度 | 当前源码事实 | 与LocalDNS的差异/意义 |
| --- | --- | --- |
| 分配器 | [memory.rs](../../../rust/native-host/src/memory.rs)：GNU/Linux用系统分配器，固定128KiB mmap阈值、规则发布后trim、进程禁THP | 已有针对性回收，不能再按“默认glibc未调优”比较；jemalloc可能有收益，需要A/B |
| 缓存容器 | [cache-core](../../../rust/cache-core/src/lib.rs)：Moka0.12.12，`max_capacity(capacity)`，没有weigher/Expiry | 条数控制，缺字节成本和按完整过期边界的主动清理；并非完全无界 |
| 缓存负载 | key、完整DNS wire、domain_set、双时钟时间、可选实际供应商origin | 保存来源和持久兼容需要成本；不能为省内存删除后声称无损 |
| 命中路径 | TTL改写生成Vec，adapter再复制修改ID/RA；域名标签也复制 | 可把一次请求自己的可变应答原地修改，保留完整缓存原件 |
| 快照与管理 | snapshot/show/dump复制key/response/domain_set，show排序/解码全量后分页；dump已有100k/64MiB/压缩16MiB限制 | 有峰值保护但仍多份复制，降低读取峰值可先做 |
| 规则 | [CompactIndex](../../../rust/matcher-core/src/compact.rs)已字符串池+精确比较；offset/result均为usize | 旧trie的21MiB历史数字不再是当前实现。仍可研究32位窄索引+宽回退 |
| 构建 | [build_mapper_matcher](../../../rust/native-host/src/config/providers.rs)仍逐条复制rule、tag、source到ValuedRule；SRS先展开文本再建索引 | 启动/热应用临时峰值仍有空间，与常驻索引压缩不同 |
| 审计 | [retention.rs](../../../rust/native-host/src/observer/retention.rs)共享模板/完整应答，数值Trace ID，逐条Arc与Box域名，保留完整SocketAddr | 已做一轮无损压缩；精简详情需要单独契约设计 |
| 排行 | [api.rs](../../../rust/native-host/src/api.rs)借用键排序，但仍按N条记录为结果Vec预留N个AuditRankItem，再产生全量排行后取limit | 低基数时多预留；新域名计数要求扫描全环，但不要求保留所有输出字符串 |
| 学习/统计 | [route_learner](../../../rust/native-host/src/route_learner.rs)分类有TTL/容量/淘汰、跨代共享；[domain_output](../../../rust/native-host/src/domain_output.rs)有262144键上限、日期共享 | 不能提议“从零补上上限/共享”；分页和持久快照仍有全量克隆 |
| UDP入口 | [udp.rs](../../../rust/native-host/src/udp.rs)每listener复用一个65535B缓冲，每包复制实际长度并spawn_local | 不是每个入站请求都持有64KiB接收缓冲 |
| UDP上游 | [upstream UDP](../../../rust/upstream-core/src/udp.rs)每在途exchange独立socket及65535B缓冲 | 慢上游/竞争并发下占用明显；每100个等待交换仅缓冲约6.25MiB，尚无当前实际峰值计数 |

Moka默认TinyLFU包含LRU与准入策略，并非没有淘汰。[官方策略说明](https://docs.rs/moka/0.12.12/moka/policy/struct.EvictionPolicy.html)。本地依赖源码还确认其存储默认64个segment；频率sketch延迟到容量一半才启用，不能声称2000万容量在启动就预分配了巨型sketch。

## 5. 小范围、保持信息完整的候选

以下“无损”指保留DNS/路由语义、完整审计事实与管理输出，不意味着CPU零成本或无需回归。

| 候选 | 作用与改动 | 范围/局限 |
| --- | --- | --- |
| S0：内存账本 | 增加每cache物理条数/live/expired、key/wire/label字节、共享origin成本、刷新/在途数；审计row/template/response基数与字节；取样区分容量/长度 | 小到中；先可放诊断构建，不能每个metrics读取都克隆全缓存。计量不等于RSS，跨cache共享要去重 |
| S1：消除命中/写入多余复制 | 保持缓存wire不可变，TTL老化后的请求私有Vec原地改ID/RA；可转移所有权的store路径接收Bytes/Vec，避免再copy_from_slice | 小；减少分配/瞬态，也可能帮助CPU。不得共享可变应答或改变DO/ECS/OPT校验 |
| S2：排行容量与top-K | 不按N为结果表预留N个String行；排序借用键并计数时统计完整distinct，仅保留准确top-K输出 | 小到中；只改变临时空间，必须保留`3687d269`完整去重总数、大小写/尾点口径、相同计数的排序与取消。100k×32B约3.05MiB仅是64位常见布局的预留估算，非已测RSS收益 |
| S3：共享读取快照 | 捕获不可变Bytes/Arc句柄，不深复制全部报文；cache show/learner/domain_output分页只对最终展示行生成字符串；dump分块编码 | 中；保持原快照时点、顺序、搜索完整IP/CNAME、格式/上限/失败事务；临时句柄本身也须有预算 |
| S4：精确窄索引 | 小于边界时offset/result使用u32，大输入回退usize，避免新增条数/总文本限制 | 小到中；两个数组由8B降4B可估计每键约省8B，20万键约1.53MiB；不是整进程已测值 |
| S5：回收真正过期数据 | 按`cache_expires_at`分批清理，而不是fresh TTL；导入/替换/flush/restart与owner同生命周期 | 中；需兼容注入时钟和单调/墙时钟换算，保留lazy。当前3000天配置下收益可能很小 |

S2可以先做避免过度reserve的更小切片，再比较top-K；不要为了省排序内存重新把distinct计数截断到top10000。S3可先做共享cache snapshot这一单元，其他分页另验，不一次横跨全部管理接口。

相同domain_set/origin、重复域名、完全相等wire还可用有界弱引用提示表共享；必须原文/全字节核对，生命周期随使用者释放。先量重复率，避免高基数时增加提示表反而占更多。不同TTL、ID、来源或ECS的记录不能凭“看上去相似”合并。

## 6. 可保持功能，但需要较大改动/独立实验

1. **分配器A/B**：对同一源码比较现有调优glibc、限制arena的glibc、jemalloc（可试报告的arena/decay组合）。jemalloc实验必须隔离现有glibc专用mallopt/trim调用，采集allocated/active/resident、碎片与空闲回收，测CPU/尾延迟及热应用。代码接入不大，完整验证面大；不能预先承诺减少多少MiB，也不增加产品运行时后端切换。
2. **规则构建借用与流式SRS**：批量共享tag/source和借用rule，避免中间ValuedRule逐行重复分配；SRS遍历直接供构建器消费，分页按同一源版本扫描。保留source顺序、regexp/keyword/AdGuard、全部marks/tags/sources、热更新失败留旧代及管理编辑/下载能力。重点收益是启动/更新峰值；多阶段构建仍须容许新旧代并存。
3. **审计分页/arena与TTL分离共享**：按页保存紧凑row、共用nonce、域名池、稳定RR内容与每条TTL分离。可以完全无损，但clear/resize/旧快照/worker取消与独立300慢查询复杂，不能让单条慢查询钉住整页。不得用当前DNS缓存重建旧日志。
4. **UDP上游接收复用**：先优化空闲缓冲保留策略/有界缓存池，再考虑复用socket与ID分发；缓存池限制空闲数，不能用池容量限制正常并发或截短报文。共享socket需验证peer/QID/question、迟到包、ID复用、取消、deadline、TCP fallback。慢上游下每个真正并发收包仍可能需要独立空间，简单池不保证降低这部分live峰值。
5. **缓存底层替换或跨层wire共享**：单线程容器可减少通用同步结构，但Moka不是目前已证明的最大项；替换涉及准入/淘汰/刷新/事务/持久快照，不作为第一步。跨层只共享完全相同不可变wire，保留各层独立key、时钟和origin。

## 7. 小改配置也能省，但属于取舍

| 方向 | 能得到什么 | 需要接受的变化 |
| --- | --- | --- |
| 缓存字节预算＋条数上限 | 让大应答/长域名有成本，限制长期工作集；这是LocalDNS最值得借鉴的产品能力 | 预算满时更早淘汰，命中率/上游负载/故障时陈旧可用性改变；DNS结果可能因再次查询上游而变化，不称严格行为无损 |
| 缩短3000天保留、降低2000万条上限 | 改动小，长期收益可能明显 | 减少历史缓存，改变lazy与离线可用性；不是释放全部“无用垃圾”，不能偷偷改默认值 |
| 少量完整详情＋较长基础日志 | 减少长期保留的特殊RR/TTL/尝试树；已有早期用户需求，可单独设计 | 较旧普通成功查询无法完整复盘，详情过期需显式标记；错误/慢查询仍要独立预算，契约/API/UI需更新 |
| 压缩存盘而非全部驻内存 | RAM换磁盘，基本事实可完整保留 | 查询延迟、I/O、故障恢复和磁盘增长控制；不等于简单mmap即不占RSS |
| 减少统计/来源/管理规则数据或限制在途请求 | 控制某类上界 | 减少历史统计/可编辑能力，或改变拥塞下拒绝/排队行为；不列入无损小修 |

Moka现有[weigher能力](https://docs.rs/moka/0.12.12/moka/sync/struct.Cache.html)可表达权重预算，不必先重写LRU。但一个max_capacity不能直接同时代表“条数”和“字节”；实现双约束/跨缓存共享总预算还需设计，不能只加一个闭包便宣称严格总预算完成。计费应覆盖元数据/容量及共享去重，并留在途与诊断余量；不承诺`cache_memory_mb`等于进程RSS。

手写DNS/JSON、删除serde、换smallvec、改hashbrown、减少socket缓冲均不单独列为必做项。rtdns已有原生DNS wire代码；有些复杂报文操作使用hickory，不能从依赖存在就判它是主要常驻内存。smallvec把空间放进外层对象，async future本身若在堆上则仍是堆内存，须看实测分布。

## 8. 建议实施顺序与验证计划

### 第一轮：先得到可解释账本，再做两项小修

建议优先 **S0 → S1 → S2**，逐项提交和比较。S0回答当前匿名驻留中缓存、审计、规则与分配器各占多少；S1针对DNS热路径；S2针对WebUI轮询/排行临时峰值。不要先重写缓存或启用分级日志。S3共享快照随后独立做；若账本证明某项极小，就不为它投入重构。

### 第二轮：单独做分配器与构建峰值实验

比较glibc/jemalloc时固定全部产品输入和保留内容，不叠加缓存预算、减少日志或改变线程运行时。构建借用/流式SRS独立比较，防止峰值变化无法归因。低CPU机器尤其要看purge/锁竞争造成的p99回退。

### 第三轮：再决策缓存预算和日志分级

先交“相同保留条目内容下的无损表示优化”结果，再交“预算下命中率/上游次数/陈旧应答可用性曲线”。实际建议的MiB预算、分配权重、日志详情条数由这两份数据决定，本报告不擅定128MiB或删除旧字段。

### 验证矩阵

- 基线是最新`3687d269`，不再退回main或旧v0.2.2；开始实施前重新检查其他会话是否推进HEAD。
- 测试只用mos-test隔离实例和可控CoreDNS。双方尽可能同机同CPU、同上游、同规则覆盖、同日志实际数量/字段、同cache驻留内容；不同产品不能声称可完全配置等价。跨产品只按可比子集说明功能差异。
- 无损候选先与最新rtdns基线逐项比较：空/热/满审计环0/100k/400k，重复域名与唯一域名、TTL轮转、复杂RR、ECS；另外独立测关闭审计，以分离成本。不是只填128题然后推算真实高基数。
- 缓存同时报告live/底层/真正过期条目、计量字节、命中率与上游次数。先维持原3000天配置，再把短TTL压力组明示为补充实验，不能悄悄降低保留后当作无损收益。
- 低延迟和慢上游分别测，记录在途交换/刷新/任务/socket数；最新UI管理并发可能高于旧版，禁止为省内存静默改回并发2。

## 9. 下一步建议

**先做可量化的无损小修：内存账本、缓存复制、排行临时空间；随后共享快照与分配器A/B。** 如果目标是长期给RAM一个可控上限，应另外设计缓存字节预算和更合理的保留策略；如果目标是让10万条完整诊断记录进一步接近LocalDNS的轻量日志占用，先比较无损分页布局，再由用户决定是否进入详情分级。

当前不能承诺优化版达到LocalDNS约24MiB，也不能把两边约36MiB驻留差额全部当作可无损消除的浪费。研究结论是具体候选和验证顺序，不是凭二进制报告直接重构程序。
